# Rapport de revue technique — MDD (backend)

Projet MDD (« Monde de Dev »), OpenClassrooms P5 option B. Revue établie le 19 septembre 2026 sur le code de `main` au commit `d2cdd31` (`back/`, Spring Boot 4.1.0, Java 21, MySQL 8.4). Les chemins sont relatifs à `back/src/main/java/com/openclassrooms/mddapi/`.

## 0. Périmètre et état du projet

**Le back-end est complet pour le MVP** : 11 endpoints (2 publics, 9 sous JWT), 5 entités JPA (`User`, `Topic`, `Subscription`, `Post`, `Comment`), 127 tests verts (126 au commit `d2cdd31`, un ajouté par la correction de l'axe p), 99,5 % d'instructions couvertes (détail dans `RAPPORT_DE_TESTS.md`). Chaque fonctionnalité des spécifications a son endpoint. L'inventaire des endpoints, les formats d'échange et d'erreur, le schéma de données et la configuration sont documentés dans `DOCUMENTATION_TECHNIQUE.md` ; cette revue ne les répète pas.

**Le front-end n'existe pas.** `front/src/app/app.routes.ts` est un tableau vide ; aucun composant, service, garde ou intercepteur n'a été écrit ; Angular Material n'est importé que pour son thème dans `front/src/styles.scss:6`, aucun composant Material n'est utilisé. En conséquence, les six indicateurs de la grille relatifs au front (« architecture front-end claire, modulaire et structurée », « conventions Angular 19 », « composants conformes aux maquettes Figma », « liaisons front/back (services, endpoints, observables/signals) », « interface responsive », « documentation des composants avec captures d'écran ») ne sont **pas réalisés**, ainsi que la FAQ utilisateur, les mentions légales et la politique de confidentialité, qui sont des pages front. Ce rapport ne les évalue pas ; il les liste en axe j.

Aucun template de revue technique n'est fourni par la mission. Étiquettes de preuve : **[code fichier:ligne]** observé dans le dépôt ; **[test Nom]** comportement verrouillé par un test ; **[mesuré]** exécuté dans cette session ; **[vault]** justification consignée dans les notes de conception du projet ; **[estimation]** ordre de grandeur, pas une mesure.

## 1. Forces

1. **L'identité vient exclusivement du jeton.** Les cinq endpoints de `UserController`, les deux endpoints de `PostController` qui identifient l'auteur et `TopicController.findAll` lisent `Long.valueOf(jwt.getSubject())` depuis `@AuthenticationPrincipal Jwt` ; aucun identifiant d'utilisateur ne transite par l'URL ni par le corps (`UpdateProfileRequest` n'a pas de champ `id`) [code `UserController.java:31-63`, `PostController.java:28-29,41-42`, `TopicController.java:23-24`]. Les ressources dont le contenu dépend de l'utilisateur vivent sous `/api/users/me/…` (profil, abonnements, fil), les ressources seulement « décorées » (`GET /api/topics` avec `subscribed`) gardent leur chemin propre [vault, critère décorée/filtrée]. Une inversion d'arguments `(userId, topicId)` est détectée par test [test `UserControllerIT.subscribe_avecJwtValideEtSucces_retourne200`, sujet `"42"`, topic `7`].

2. **Chargement anticipé maîtrisé, N+1 exclu sur les lectures principales.** Fil et détail d'article : `@EntityGraph(attributePaths = {"user", "topic"})` sur `findPostsByUserId` et `findWithUserAndTopicById` [code `PostRepository.java:16-21`] ; commentaires avec auteur en une requête [code `CommentRepository.java:12-13`] ; abonnements du profil avec topic [code `SubscriptionRepository.java:18-19`]. Liste des topics avec statut d'abonnement en **deux requêtes fixes** et jointure en mémoire par `HashSet` [code `TopicService.java:24-32`]. Le chargement anticipé est **prouvé** par `Hibernate.isInitialized(...)` avant tout accès pour trois des quatre graphes [test `PostRepositoryIT` (`findWithUserAndTopicById`), `SubscriptionRepositoryIT`, `CommentRepositoryIT`] ; celui du fil ne l'est pas (axe b). Là où seul l'id est nécessaire, `getReferenceById` évite un `SELECT` [code `PostService.java:66,101`, `UserService.java:85`] ; `addComment` utilise volontairement `findById` sans graphe, l'article n'étant lu que pour son existence [code `PostService.java:98`].

3. **Double garde contre le double abonnement.** Contrôle applicatif `existsByUserIdAndTopicId` → `AlreadySubscribedException` (409) [code `UserService.java:81-83`], puis filet en base : contrainte `UNIQUE (user_id, topic_id)` nommée `UniqueUserAndTopic` [code `model/Subscription.java:9-17`] dont la violation est traduite en 409 à message générique, sans détail SQL [code `GlobalExceptionHandler.java:62-65`, test `UserControllerIT` sur `DataIntegrityViolationException`].

4. **Mise à jour du profil sans faux conflit ni écrasement du mot de passe.** L'unicité n'est vérifiée que si la valeur change, et en excluant l'utilisateur courant (`existsByEmailAndIdNot`) [code `UserService.java:59-64`, `UserRepository.java:18-19`]. Mot de passe `null` ou blanc → hash inchangé ; sinon ré-encodé BCrypt [code `UserService.java:68-70`]. Aucun DTO de réponse ne porte `passwordHash` [code `dto/UserResponse.java`, `UserProfileResponse.java`, test `AuthControllerIT`/`UserControllerIT` `jsonPath("$.passwordHash").doesNotExist()`].

5. **Règles de mot de passe identiques à l'inscription et à la mise à jour**, bornées à 72 caractères parce que BCrypt tronque au-delà, jeu de caractères spéciaux `\p{Punct}` documenté en Javadoc sur le champ [code `dto/RegisterRequest.java:20-40`, `UpdateProfileRequest.java:25-30`]. Le hachage est verrouillé par `ArgumentCaptor` : une mutation qui stockait le mot de passe en clair est aujourd'hui détectée [test `AuthServiceTest.register_emailEtUsernameLibres_sauvegardeEtRetourneUnToken`]. Le champ n'était pas déclaré obligatoire à l'inscription au commit `d2cdd31` ; corrigé depuis (axe p).

6. **Contrat d'erreur unique et sans fuite.** Un seul `@RestControllerAdvice`, dix handlers, un DTO `ErrorResponse` ; les erreurs de validation renvoient `fieldErrors` indexé par nom de champ et message d'annotation, jamais la valeur rejetée [code `GlobalExceptionHandler.java:21-30`]. Les six exceptions métier suivent un patron uniforme (`extends RuntimeException`, message constant dans le service) et sont mappées par un `buildResponse` privé [code `GlobalExceptionHandler.java:32-80`]. Aucun `TODO`/`FIXME`, aucun logger applicatif qui pourrait tracer un secret [mesuré, grep sur `src/main`].

7. **Séparation stricte DTO / entité, entités immuables, responsabilités nettes.** Aucun contrôleur n'importe `model.*` ; les services ne retournent que des DTO [code imports des quatre contrôleurs]. `Post`, `Comment`, `Subscription`, `Topic` ont des champs `final` et pas de setter ; seul `User`, le seul objet modifié, est mutable [code `model/*.java`]. Associations unidirectionnelles `@ManyToOne(fetch = LAZY)` uniquement, aucun `@OneToMany`, aucun `cascade` [code `model/Post.java:28-34`, `Comment.java:21-27`, `Subscription.java:26-32`]. Côté SOLID : chaque service porte un seul agrégat (responsabilité unique), les contrôleurs ne contiennent que l'extraction du `sub` et l'appel de service (`UserController.java:31-63` : aucune logique), toutes les dépendances sont injectées par constructeur sur des champs `final` ; l'entorse connue est `UserController` qui dépend de `PostService` pour le fil [code `UserController.java:24`], conséquence du placement du fil sous `/users/me` (§4).

8. **Secrets hors du dépôt, même en développement.** `application.properties` ne contient ni mot de passe ni clé ; `application-local.properties` (gitignoré, jamais suivi — vérifié par `git ls-files` et `git log --all`) ne porte que `spring.datasource.password=${MYSQL_PASSWORD}` et `mdd.jwt.secret=${JWT_SECRET}`, à fournir comme variables d'environnement [code `application.properties:9-11`, `.gitignore:8-9`, mesuré]. Le `.env` racine n'est lu nativement que par `docker-compose.yml` ; pour Maven il doit être exporté à la main (axe c).

9. **JWT avec les primitives Spring Security, algorithme explicite.** `NimbusJwtEncoder`/`NimbusJwtDecoder` sur une clé HMAC-SHA256 [code `security/jwt/JwtConfig.java:24-39`], `JwsHeader.with(MacAlgorithm.HS256)` forcé dans `JwtService` [code `JwtService.java:37`], claims réduits à `iss`, `iat`, `exp`, `sub` [code `JwtService.java:30-35`] ; session `STATELESS`, CSRF désactivé (aucun cookie), deux routes publiques seulement, tout le reste `authenticated()` [code `SecurityConfig.java:29-36`]. CORS restreint aux origines de `mdd.cors.allowed-origins`, aux cinq méthodes utilisées et aux en-têtes `Authorization`/`Content-Type` [code `SecurityConfig.java:46-55`].

10. **Désabonnement en une instruction, idempotent.** `DELETE` JPQL `@Modifying` sans charger l'entité ; 204 même si l'abonnement n'existait pas, 404 seulement si le topic n'existe pas [code `SubscriptionRepository.java:24-26`, `UserService.java:91-96`, `UserController.java:50-55`]. Une mutation retirant la condition `user_id` — qui aurait désabonné tous les utilisateurs — est détectée [test `SubscriptionRepositoryIT.deleteByUserIdAndTopicId_deuxUtilisateursAbonnesAuMemeTopic_neSupprimeQueCeluiVise`].

11. **Qualité des tests vérifiée, pas seulement mesurée.** JaCoCo (`pom.xml`, agent unique Surefire + Failsafe, rapport en `verify`) a localisé les zones non exécutées ; la preuve par mutation manuelle a ensuite révélé quinze mutations non détectées par la suite, corrigées par sept tests ajoutés et vingt-trois renforcés sans toucher au code de production (détail dans `RAPPORT_DE_TESTS.md` §5).

## 2. Axes d'amélioration

Chaque axe a été vérifié dans le code de `main` ; l'étiquette indique s'il était déjà consigné dans un document du dépôt. Deux axes sont corrigés à la suite de cette revue : la Javadoc (axe k, commits `docs(<package>)` de la branche de livraison) et l'anomalie de validation (axe p, commit `9581c70`). Les autres restent ouverts, avec une recommandation chiffrée au §3.

- **a. Aucun test de JWT présent mais invalide ou expiré** [déjà consigné : `TESTS_REVIEW.md`]. Le `JwtDecoder` des tests de contrôleur est un `@MockitoBean` jamais stubbé et l'authentification de test contourne le filtre Bearer ; la chaîne « en-tête → décodage → 401 » n'est exercée par aucun test [mesuré : aucun `when(jwtDecoder`, aucune `JwtException` dans `src/test`]. Le cas le plus fréquent en production (retour après 24 h) est sans filet.

- **b. Aucun test de câblage bout-en-bout ni end-to-end ; un chargement anticipé non prouvé** [déjà consigné, complété]. Le seul `@SpringBootTest` (`MddApiApplicationIT`) ne fait aucun appel HTTP ; l'aller-retour réel encodage/décodage HMAC de `JwtConfig` n'est exécuté que par le démarrage du contexte ; CORS n'est pas testé. Le `@EntityGraph` de `findPostsByUserId` — le fil, requête la plus exposée au N+1 — n'est pas asserté par `Hibernate.isInitialized` dans `PostRepositoryIT.findPostsByUserId_*` [code `PostRepository.java:16`, test `PostRepositoryIT`] : le retirer passerait inaperçu.

- **c. Configuration de développement dans le profil commun, aucun profil de production, aucune migration versionnée, secret exigé par les tests** [observé]. `spring.jpa.hibernate.ddl-auto=update`, `spring.jpa.show-sql=true`, `format_sql=true` et `spring.profiles.active=local` codé en dur sont dans `application.properties` [code `:4,14-16`] ; il n'existe ni `application-prod.properties` ni dépendance Flyway/Liquibase [mesuré, grep `pom.xml`]. En l'état, un déploiement afficherait chaque requête SQL dans les logs et laisserait Hibernate modifier le schéma. De plus, `./mvnw verify` échoue sur un clone frais : `MddApiApplicationIT` charge `JwtConfig`, qui exige `mdd.jwt.secret`, absent de `application.properties` et résolu par `${JWT_SECRET}` dans un fichier gitignoré [mesuré : `Could not resolve placeholder 'JWT_SECRET'` sans la variable].

- **d. Aucune limitation des tentatives de connexion ; énumération des comptes possible** [observé ; limite assumée dans le vault]. `POST /api/auth/login` peut être appelé sans borne ; la seule protection est le coût de BCrypt [mesuré : aucun `bucket4j`/`ratelimit` dans `pom.xml` ni `src`]. Le 409 distinct de l'inscription (« Cet email est déjà utilisé ») confirme l'existence d'un compte [code `AuthService.java:36-37`].

- **e. Deux réponses hors format `ErrorResponse`** [déjà consigné : `TESTS_REVIEW.md`]. Le 401 (jeton absent, invalide, ou identifiants faux au login) est rendu par le `BearerTokenAuthenticationEntryPoint` par défaut — corps vide, en-tête `WWW-Authenticate` [code `SecurityConfig.java:32-33`, aucun `AuthenticationEntryPoint` custom ; test `AuthControllerIT.login_identifiantsInvalides_retourne401`]. Le JSON malformé (`HttpMessageNotReadableException`) n'a pas de handler : corps vide sous MockMvc [test `register_corpsJsonMalforme_retourne400`], et dans un conteneur réel probablement le JSON de `BasicErrorController` — forme non figée par un test [TESTS_REVIEW « Le contrat d'erreur de l'API »]. Le front devra traiter au moins trois formes d'erreur.

- **f. Décodeur sans validation d'émetteur ; jeton de 24 h sans refresh ni révocation** [observé]. `NimbusJwtDecoder.withSecretKey(key).build()` n'installe que la vérification de signature et d'expiration ; le claim `iss` émis n'est jamais vérifié [code `JwtConfig.java:33`, `JwtService.java:31`]. `mdd.jwt.expiration-minutes=1440` sans mécanisme de renouvellement : un jeton volé reste valide jusqu'à 24 h [code `application.properties:21`]. La longueur de la clé Base64 n'est pas contrôlée au démarrage [code `JwtConfig.java:36-39`].

- **g. Fil non paginé** [observé ; choix assumé dans le vault]. `findPostsByUserId` retourne `List<Post>` sans `Pageable` ; tout le fil est chargé puis mappé [code `PostRepository.java:16-18`, `PostService.java:41-51`]. Acceptable au volume du MVP, bloquant au-delà.

- **h. Une seule violation par champ dans `fieldErrors`** [observé]. `handleValidation` accumule dans une `HashMap` indexée par nom de champ : un mot de passe violant `@Size` et `@Pattern` ne remonte qu'un des deux messages, choisi par l'ordre de validation [code `GlobalExceptionHandler.java:23-26`].

- **i. Incohérences transactionnelles mineures** [observé]. `TopicService.findAllWithSubscriptionStatus` est la seule lecture composite sans `@Transactional(readOnly = true)` [code `TopicService.java:23`] ; `AuthService.register` enchaîne deux `exists` et un `save` hors transaction, la course entre deux inscriptions simultanées n'étant tranchée que par les contraintes `UNIQUE` (→ 409 générique) [code `AuthService.java:32-52`, `model/User.java:19-23`].

- **j. Front-end inexistant** [observé, §0]. Bloque les tests end-to-end, les captures d'écran, l'analyse des besoins front, la FAQ utilisateur, les mentions légales et la politique de confidentialité — tous exigés comme livrables.

- **k. Documentation du code** [observé]. Au commit `d2cdd31`, aucune classe de `src/main` ne porte de Javadoc (0/45 fichiers, mesuré) ; seuls deux champs de DTO en ont une (`RegisterRequest.password`, `UpdateProfileRequest.password`).

- **l. Documents de `back/docs/` partiellement périmés** [observé]. Les trois `*_MERGE_AUDIT.md` décrivent l'endpoint d'abonnement à un emplacement abandonné depuis (`/api/topics/{id}/subscribe` → `/subscription` par la PR #9 → `/api/users/me/subscriptions/{topicId}` par la PR #12) et un `GET /api/auth/me` « conservé » qui a été supprimé (PR #13) ; seul `TOPICS_MERGE_AUDIT.md` porte une note datée, qui s'arrête au renommage de la PR #9. Les trois `*_TEST_CHECKLIST.md` (74 scénarios) n'ont jamais été exécutées. Ces documents sont des journaux datés, exacts à leur date ; ils ne doivent pas être lus comme l'état courant.

- **m. Écart de versions avec la grille** [observé]. La grille cite « Angular 19 » et « Spring Boot 3 » ; le projet utilise Angular 21.2 et Spring Boot 4.1.0 [code `pom.xml:8-9`, `front/package.json`]. Le choix est justifié (Boot 3.5 en fin de support en juin 2026 [vault]) mais entraîne des écarts de forme à connaître : `@MockitoBean` au lieu de `@MockBean`, starters de test éclatés (`webmvc-test`, `data-jpa-test`, `security-test`), packages `org.springframework.boot.*.test.autoconfigure`.

- **n. Documentation d'API absente du code et du dépôt de départ** [observé]. Pas de `springdoc-openapi` dans `pom.xml`, `README.md` racine encore celui du squelette Angular 14 fourni, aucune description des endpoints dans `back/` au commit `d2cdd31` en dehors des tests [mesuré]. `DOCUMENTATION_TECHNIQUE.md`, ajouté sur la branche de livraison, couvre désormais endpoints, formats et schéma ; il reste écrit à la main, donc à maintenir à chaque changement de contrat.

- **o. Aucun analyseur statique ni formateur ; formatage inégal** [observé]. `pom.xml` ne contient ni Checkstyle, SpotBugs, PMD, Sonar ni Spotless [mesuré]. Écarts visibles : `if(` sans espace [code `AuthService.java:36,39`], bloc de setters sur-indenté [code `AuthService.java:44-46`], `private  SecretKeySpec buildSecretKey(){` [code `JwtConfig.java:36`], `class User{` [code `model/User.java:13`], indentation à 5 espaces [code `model/Topic.java:23`]. Sans effet fonctionnel, mais visibles en relecture.

- **p. Mot de passe non obligatoire à l'inscription — anomalie réelle, identifiée puis corrigée.** Au commit `d2cdd31`, `RegisterRequest.password` portait `@Size` et `@Pattern` mais pas `@NotBlank`, contrairement à `email`, `username` et à `LoginRequest.password` [code `RegisterRequest.java:11-40`, `LoginRequest.java:13`]. Bean Validation accepte `null` pour ces deux contraintes : un corps d'inscription sans champ `password` franchissait la validation. Aucun test ne couvrait ce cas (les huit `register_*` de `AuthControllerIT` testaient email invalide, motif, longueur, username court, JSON malformé).
  *Découverte* : par la relecture adverse de ce rapport, menée par un agent en contexte neuf ne voyant que le rapport et le code — après un audit qualité des tests en quatre lots (preuve par mutation, `TESTS_REVIEW.md`) qui ne l'avait pas vue, parce que la mutation ne renforce que des tests existants et qu'aucun test n'envoyait un corps sans mot de passe.
  *Comportement réel mesuré avant correction* [mesuré, branche `fix/validation-mot-de-passe-obligatoire`] : la lecture statique de cette revue annonçait un 500 par `IllegalArgumentException` ; le test écrit avant la correction a montré autre chose. Sous `@WebMvcTest` (service mocké) : **201 à corps vide, service appelé**. En contexte complet sur MySQL : `BCryptPasswordEncoder.encode(null)` **renvoie `null`** dans `spring-security-crypto 7.1.0`, l'`INSERT` viole `password_hash NOT NULL` et le client reçoit un **409** `ErrorResponse` « La ressource entre en conflit avec une contrainte existante » — un statut faux et un message trompeur, pas un 500. Aucun compte n'est créé.
  *Correction* : `@NotBlank(message = "Le mot de passe est obligatoire")` sur `RegisterRequest.password`, test `register_motDePasseAbsent_retourne400EtServiceJamaisAppele` (écrit d'abord, en échec : 400 attendu, 201 obtenu), inventaire des cinq DTO d'entrée — seul ce champ était concerné ; `UpdateProfileRequest.password` reste sans `@NotBlank` par intention (`null` = mot de passe inchangé), désormais dit en Javadoc. 127 tests verts, couverture inchangée. Le cycle découverte → mesure → correction → documentation est lui-même un enseignement de cette revue : une hypothèse de lecture (« 500 ») a été corrigée par la mesure.

## 4. Choix structurants : avantages et inconvénients

Justifications détaillées dans les notes de conception du projet [vault] ; une ligne par choix, en réponse à la demande du responsable technique de « rester objectif sur les avantages et inconvénients ».

| Choix | Pour | Contre |
|---|---|---|
| Monolithe en couches (`controller/service/repository/model/dto/security/exception`) plutôt que micro-services proposés par le client | Un seul déploiement, transactions locales, proportionné à 5 entités et un développeur | Pas de scalabilité indépendante par fonctionnalité ; le découpage par couche mêle les domaines là où une ressource en croise deux (`UserController` dépend de `PostService` pour le fil [code `UserController.java:24`]) |
| Services concrets sans interface, mapping DTO inline sans MapStruct | Moins de fichiers ; Mockito mocke les classes concrètes sans interface | Un second consommateur ou une seconde implémentation imposerait un refactoring ; duplication de la construction de `TopicResponse` dans `TopicService.java:28-33` et `UserService.java:45` |
| Spring Data JPA + MySQL 8.4 (hérités du prédécesseur) | `@EntityGraph`, JPQL, `getReferenceById` couvrent tous les besoins ; même image Docker en dev et en test | `LONGTEXT` lie l'entité à MySQL [code `model/Post.java:25`] ; `ddl-auto=update` ne remplace pas une migration |
| JWT via `JwtEncoder`/`JwtDecoder` natifs Spring Security plutôt que jjwt | Aucune dépendance externe, filtre Bearer et 401 fournis, contrainte client « privilégier les modules Spring » | API moins documentée en tutoriels ; HS256 à forcer explicitement (correctif #11) |
| Jeton stateless 24 h, `sub` = id, pas de logout serveur ni de rôles | Aucun état côté serveur ; email et username restent modifiables sans invalider le jeton | Pas de révocation ; un seul niveau d'autorisation |
| Testcontainers MySQL plutôt que H2 | Même dialecte qu'en production (`LONGTEXT`, sous-requêtes `IN (SELECT…)`) | Docker requis pour `mvn verify` ; démarrage du conteneur de l'ordre de 10 s [estimation] |
| Preuve par mutation manuelle plutôt que PIT | Aucune dépendance, ciblée sur les tests jugés faibles, a révélé 15 mutations non détectées | Non rejouable automatiquement ; dépend de la rigueur du relecteur — l'anomalie p lui a échappé |
| Contrat d'erreur : 401 et JSON malformé laissés au comportement Spring par défaut | Pas de duplication d'un comportement natif, pas de risque de divergence avec les cas d'expiration | Au moins trois formes d'erreur pour le front (axe e) |
